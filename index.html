Enterprise messaging · OpenTelemetry · Splunk Observability Cloud

Unified messaging observability demo

One OpenTelemetry Collector ingests IBM MQ, Kafka, and RabbitMQ metrics into Splunk Observability Cloud — alongside APM traces from instrumented MQ sample apps. Built for customers who run multiple messaging platforms today (often with platform-specific extensions) and want a single observability backend.

Splunk value adds

Talking points when the customer compares Dynatrace extensions, AWS Distro OTel, and Grafana today.

Value add — One collector, one backend

Replace three extension patterns (MQ, Kafka, RabbitMQ) with one OTel Collector and one Splunk Observability Cloud tenant. Same deployment model they already use with AWS Distro of OpenTelemetry — add Splunk exporters alongside existing pipelines.

Value add — OpenTelemetry-native, vendor-neutral instrumentation

MQ metrics via OpenTelemetry Java Contrib; Kafka/Rabbit via standard collector receivers. No proprietary agent per platform — aligns with enterprise OTel strategy.

Value add — Metrics + APM correlation in one UI

When ibm.mq.queue.depth spikes, jump to APM traces for order-producer / order-consumer and see mq.put.order / mq.get.order spans — tie infrastructure signals to application behavior without switching tools.

Value add — Scale-ready metric model

Same dimensions they need at production scale: queue, queue_manager, deployment.environment. Detectors on sustained depth, scrape failures, and consumer lag apply across thousands of queues with grouping — not one-off dashboards per extension.

Value add — Complements IR360, does not replace it

IR360 remains the capacity/planning tool for MQ estate. Splunk O11y is the real-time operations layer: alerting, incident drill-down, and cross-platform correlation with Kafka/RabbitMQ on AWS/Azure.

Troubleshooting value — Faster MTTR across platforms

Ops teams today chase the same symptoms in three places (MQ extension, Kafka extension, Rabbit extension). Splunk gives one symptom → metric → service → root cause path for backlog, lag, and scrape failures — with detectors that group by queue, queue_manager, or consumer group instead of rebuilding dashboards per platform.

At scale — hundreds or thousands of queues

Not one collector or YAML file per queue. Queues are dimensions on shared metrics (e.g. ibm.mq.queue.depth with queue=…, queue_manager=…). You deploy collectors and sidecars per host, cluster, or queue manager, then use filters and Splunk grouping — same pattern as Dynatrace MQ extension at State Street scale.

PlatformWhat you deployHow queues are coveredCardinality control
IBM MQ One ibm-mq-metrics sidecar per queue manager (or pod per QM in K8s) · one collector can receive OTLP from many sidecars Sidecar queueFilters in config.yml — include/exclude patterns (e.g. ORDER.*, exclude SYSTEM*), not a line per queue · multiple QMs in one sidecar config file Tier 1: all business queues via wildcards · Tier 2: exclude temp/system · Tier 3: split sidecars by QM or region if PCF load is high · increase numberOfThreads for large estates
RabbitMQ One rabbitmq receiver per management endpoint (node or load-balanced API) Receiver discovers all queues automatically via management API — zero queue names in YAML Alert on critical vhost/queue name patterns in Splunk detectors · optional: separate receivers per vhost/cluster for isolation
Kafka One kafkametrics receiver per cluster (bootstrap brokers) Scrapers for brokers, topics, consumer groups — topics are dimensions, not config entries topic_match and group_match regex to skip internal topics (^[^_].*$ default) · one config template per cluster, not per topic

Deployment tiers (typical enterprise)

  1. Collector gateway — regional or platform OTel Collectors (EKS/ECS/VM) with one metrics pipeline → signalfx. Many MQ sidecars and app agents send OTLP inward.
  2. Edge / per-QM sidecar — Java Contrib beside each queue manager; same YAML template, swap QM host/name via env or Helm values.
  3. Splunk layer — one detector on ibm.mq.queue.depth grouped by queue_manager + queue; top-N charts; filter queue:ORDER.* — not 1,000 dashboards.
  4. GitOps — one Helm chart / Ansible role: collector config is static; queueFilters and env vars vary per QM from inventory (CMDB, IR360 export, tags).

Say this — vs “one config per queue”

“Dynatrace MQ extension does not need a JSON file per queue either — it discovers queues and alerts on dimensions. OTel is the same: one scrape path, many time series. You tune include/exclude filters and Splunk detectors, not collector count. IR360 still owns capacity planning for thousands of queues; Splunk owns which queue is breaching SLA right now.”

This lab’s live Compose config merges all three messaging paths: collector/otelcol-config.yaml.

Gotcha — use deployment.environment.name

Metric Explorer global filter: deployment.environment.name:messaging-demo-lab

Do not assume deployment.environment:messaging-demo-lab works in the UI — Splunk often indexes/filters on the .name dimension for environment scoping. APM service views may accept either; start with .name if metrics look empty.

Gotcha — traces visible but no metrics?

  1. Same token path as traces: metrics export via OTLP HTTP to /v2/datapoint/otlp (traces use /v2/trace/otlp). After changing .env.splunk, run docker compose up -d otel-collector.
  2. Restart MQ metrics sidecar: docker compose restart ibm-mq-java-metrics — it logs Exporter failed if the collector was down when it started.
  3. MQ sidecar exporting to wrong host: if logs show Failed to connect to localhost:4317, rebuild the sidecar — it must use http://otel-collector:4318 (HTTP/protobuf), not gRPC on localhost.
  4. Try without the environment filter first: search ibm.mq.queue.depth or rabbitmq.message.current with no filter, then add deployment.environment.name:messaging-demo-lab.
  5. Metric names differ from legacy integrations: OTel Rabbit = rabbitmq.message.current (dim message.state=ready), not old gauge.queue.messages_ready from collectd/Dynatrace.
  6. Rabbit needs a queue: run bash scripts/load-rabbit-traffic.sh 10 — empty Rabbit has no queue-level metrics.
  7. MQ sidecar: if logs show Exporter failed, run docker compose up -d --build ibm-mq-java-metrics otel-collector (sidecar waits for collector on startup).

IBM MQ — concepts & metrics

101: A queue manager (QM1 in this lab) owns queues — named buffers where messages wait. Applications connect through a channel (DEV.APP.SVRCONN for apps, MQOTEL.SVRCONN for the metrics sidecar). Producers PUT to ORDER.REQ; consumers GET. If GET stops, depth rises — the primary backlog signal.

ibm.mq.message.enq.countMessages put (enqueued) on the queuequeue, queue_managerConfirm producers still sending
ibm.mq.message.deq.countMessages got (dequeued) from the queuequeue, queue_managerConfirm consumers still reading; enqueue >> dequeue → depth grows
ibm.mq.manager.statusQueue manager healthqueue_managerQM down = all queues on that QM affected

Kafka — concepts & metrics

101: Producers write to a topic split into partitions (ordered logs). Consumer groups read independently; each partition is consumed by one member in the group at a time. Lag = how far a consumer group’s offset is behind the latest message — Kafka’s equivalent of queue depth.

kafka.broker.*Broker throughput, request handlers, networkbroker id, clusterBroker overload or under-provisioned cluster

kafka.consumer.lag (and related)Messages / offset behind log end per partitiontopic, partition, consumer groupPrimary backlog alert — same story as MQ depth

RabbitMQ — concepts & metrics

101: Producers publish to an exchange; routing rules deliver copies to queues. Consumers receive messages; until they ack, messages can sit in unacknowledged state. Ready = waiting in the queue; unacked = delivered but not confirmed. This lab uses queue demo.orders on the default vhost /.

Gotcha — Rabbit metrics look like zero

  • Use rabbitmq.message.current with dimension message.state=ready for backlog count — not legacy names like gauge.queue.messages_ready.
  • Rate metrics (rabbitmq.message.published, *_details.rate) show 0 when idle — that is normal if you are not actively publishing. Depth-style metrics should match Management UI “Ready”.
  • Cumulative counters (rabbitmq.message.published) only increase; plot rate or use delta if you want “messages/sec”.
  • Queue must exist before queue-level series appear — run load-messaging-demo or load-rabbit-traffic.sh.
  • In Metric Explorer, pick aggregation latest or mean for gauge-like depth; avoid max over long windows on sparse scrapes.

Splunk access token

Required for metrics and APM to appear in Splunk Observability Cloud. The local demo stack runs without it; Splunk ingest does not.

Where to put your token

Create or edit .env.splunk in the repo root (same folder as docker-compose.yml). This file is gitignored — your token stays on your machine only.

Step 1 — Create the file

Terminal
cd MQ-Rabbit-Kafka
cp .env.splunk.example .env.splunk

Step 2 — Paste your ingest token

Open .env.splunk in Cursor or your editor and replace the placeholder on SPLUNK_ACCESS_TOKEN:

.env.splunk
SPLUNK_REALM=us1
SPLUNK_ACCESS_TOKEN=paste-your-ingest-token-here
SPLUNK_INGEST_URL=https://ingest.us1.signalfx.com
SPLUNK_API_URL=https://api.us1.signalfx.com
  • Use an Ingest access token (not an API token).
  • No quotes around the token. No spaces around =.
  • If your org is us0, eu0, etc., change SPLUNK_REALM and both URLs to match (see .env.splunk.example comments).

Step 3 — Get a token in Splunk O11y

  1. Open Splunk Observability Cloud → Settings (gear) → Organization Settings
  2. Access Tokens → New Token
  3. Type: Ingest → create and copy the token (shown once)
  4. Paste into .env.splunk as SPLUNK_ACCESS_TOKEN

Step 4 — Restart the collector (and MQ metrics sidecar)

Terminal
docker compose up -d otel-collector
docker compose restart ibm-mq-java-metrics
docker compose logs otel-collector --tail 20

Look for Everything is ready in collector logs — not auth/401 errors. If APM traces work but metrics do not, the sidecar restart fixes most MQ metric gaps.

Step 5 — Confirm data in Splunk

  1. Run bash scripts/run-demo.sh or load traffic scripts
  2. Metric Explorer → filter deployment.environment.name:messaging-demo-lab
  3. Search ibm.mq.queue.depth, kafka, or rabbitmq
  4. APM → services order-producer, order-consumer, inventory-service

Do not commit .env.splunk

Only .env.splunk.example (placeholder values) belongs in git. If you accidentally commit a token, revoke it in Splunk and create a new one.
